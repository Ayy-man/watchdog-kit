# watchdog-heartbeats

You are giving the watchdog its first eyes: a record that each scheduled job ran, a way to know the schedule and the code agree, an adapter and a proof-of-proof per door, and two database identities, a reader that can only see what the egress policy allows and a writer that can only touch the watchdog's own tables. Read `../watchdog-build/references/shared-contract.md` first, then `.watchdog/CONTRACT.md`, `.watchdog/MAPPING.md` and `.watchdog/EGRESS.md`, and confirm the journal holds the human's approval of scopes and egress before you write a line into the repo; the roles you create enforce that approval. If `lib/watchdog/core/VERSION` is not in the repo yet, run `node $KIT/scripts/vendor-core.mjs <repo root>` from the repo root; it copies the core with its stamp and `--check` later confirms parity.

Read `## Stack` in `MAPPING.md` before anything else. The wrapper below assumes a Fetch-style handler (it takes a `Request` and returns a `Response`) and the role assumes Postgres; a job or a door whose stack line reads `unsupported` gets no wrapper and no role grant, and stays listed as unsupported with what it would take, because a wrapper written for the wrong handler shape can change the response it was meant to observe.

## 1. State the wrapper contract before writing the wrapper

Copy `$KIT/templates/HEARTBEATS.md` to `.watchdog/HEARTBEATS.md` before writing any code. Its `## Wrapper` section states the wrapper contract, and you keep it true in every line of code that follows, because a watchdog that can cause a failure in the job it watches has made the app less reliable than it found it. `$KIT/core/cron-run.js` and `$KIT/core/job-run.js` implement it; read their headers rather than re-deriving the rule.

## 2. Wrap every cron, or map the existing heartbeat table

Read `## Existing monitoring` in `MAPPING.md` first and choose one primary proof source per scheduled job. Where an existing job-receipts table, a cron check-in or the scheduler's own run history already establishes that the job ran, reuse it; add a wrapper only where that proof is missing or too weak, and record the gap that justifies it.

Take the schedule from `.watchdog/MAPPING.md` (the host's cron config, task-runner tasks, `pg_cron` jobs, CI schedules, or whatever other scheduler the survey named). For each scheduled route that needs new instrumentation, wrap its handler with `runCronJob('<job name>', request, handler, { client })` so a scheduled call records a `job_runs` row at start and closes it at the end with a trimmed summary (counts and reasons, never the rows it touched), and an early exit is recorded as skipped with its reason so a skipped slot reads differently from a missed one. `client` is the watchdog's database client from step 6, built in one small module of the client's (`lib/watchdog/db.js`) so every heartbeat, the sweep and the checks get their connection from one place; pass `clientFactory(env)` instead where the client is built per request, and let it return null to skip the heartbeat when the writer is not configured. Only a call carrying the scheduler's shared secret is recorded (a bearer token the scheduler sends; `secretName` defaults to `CRON_SECRET`, so pass the client's own variable name where it differs), so an unauthenticated hit never adds rows. A scheduler that sends no secret at all is recorded as such under `## Jobs`, and its jobs are mapped from its run history rather than wrapped.

Copy the six core migrations, `$KIT/core/sql/0001_watchdog_findings.sql` to `0006_alert_sends.sql`, into the client's migration path in that order (findings, reviews, job runs, sweeps, silences, alert sends; `0007_finding_id_v2.sql` is an upgrade template for installations on ids older than 0.2 and is never applied on a new build), each under the client's own timestamp convention, and apply them one file at a time, never a bulk push. The live dry run that follows this phase writes findings and sweeps, so all of them must be in the ledger first; `alert_sends` stays empty at report-only and is created now so the alert door has its proof table from the start. A client that already has a `job_runs` table of the core's shape keeps it and skips 0003. Each core file enables row-level security with a placeholder policy; where the client's database does not use row-level security, keep the `enable` line harmless and rely on the grants in step 6, and say which under `## Role`.

When existing records supply the proof (a job-receipts table, cron check-ins, scheduler run history), write a read adapter rather than a second recording path. It exposes the fields the checks need without copying records into `job_runs` or changing the source, and it preserves what the source holds: identity, scope, the scheduled occurrence, run and attempt ids, start and finish, terminal result, observation time. Never invent a success or a missing timestamp to fit the `job_runs` shape; a queued run is not a started run, and a finished handler does not establish the business end state. Record under `## Jobs` which source each job uses and what that source cannot establish. A job with no proof from any source is finding 0.

Declare two more facts per job in `## Jobs`, because a heartbeat that only says "it ran" misses the two ways a job fails while looking alive. `max_runtime`: a run that started and has not finished past it is `job_stuck`, which also catches a slot whose previous run was still going when the next began. `work_floor`: the summary count the job is expected to produce on a slot that has work (the number of reminders due, the number of rows in the queue), computed from the app's own data for that slot, so a run that finished `ok` with a summary below the floor is `job_did_nothing`, the failure the operator notices last. A job whose floor cannot be computed from data says so and gets no `job_did_nothing` check. Where the scheduler is `pg_cron`, the primary proof source is `cron.job_run_details` reconciled in SQL against the schedule in `cron.job`, with no wrapper at all: expected fire times are computed from the schedule and left-joined to the runs, and the status and return message of each run are the evidence.

## 2a. Build the sweep itself

The watchdog is a scheduled job too, and nothing else in the build creates it. Write the sweep route in the client's framework (in a file-routed framework, a route file at `api/watchdog/sweep` exporting `GET`) around `runWatchdog` from `lib/watchdog/core/run.js` with the client's scope, zone and the check list (empty until checks exist; the route still records a sweep), wrapped in `runCronJob('watchdog.sweep', ...)` so every sweep is itself a heartbeat, gated by the scheduler's secret, and add it to the scheduler every 30 minutes (two entries only where the client's scheduler needs a daylight-saving pair). `runWatchdog` takes one client, writes the watchdog's tables through it and hands each check a read-only wrapper of it, so pass it the routing client from `lib/watchdog/db.js` (step 6), never a single connection that can both read app data and write. Register the core's self check, `sweepSelfCheck` from `lib/watchdog/core/self-check.js`, as the first check: it raises `sweep_missed` for a slot with no sweep row and `check_error` is already the core's. The live stale alarm (no finished sweep in two cadences) cannot come from inside a sweep that is not running, so it is computed by the page from `job_runs` with `staleAlarm` from the same module and by the hub from the projection; say both under `## Jobs`. Add a manual trigger (`watchdog.sweep.manual`) for the live dry runs, token-gated, logged under its own job name so a hand-started sweep never reads as a scheduled one.

## 3. Prove the schedule matches the code

Write a schedule parity eval (`scripts/eval-job-schedule.mjs`): it reads the scheduler config and the declared jobs with their primary proof source, wrapped or mapped, and fails when a scheduled path has no declared source, a declared job is not scheduled, or two entries differ only by the daylight-saving pair without the route checking the wall-clock hour. A mapped job needs no wrapper; a missing live proof is a door finding, not a parity failure.

Beside it, write the contract drift eval (`scripts/eval-contract-drift.mjs`): it enumerates the doors the way the survey did (the same type-aware or grep walk, recorded in `MAPPING.md`) and fails when a route handler, a scheduled job or a provider call site exists that `.watchdog/CONTRACT.md` does not list, or when a listed door no longer exists in the code. The contract is the watchdog's whole model of the app, and without this eval it rots silently: a new webhook route or a new provider client is a door with no proof, which is finding 0, and nothing would say so. The eval runs with the app's test suite so the diff is seen in the change that caused it. If the walk used the `typescript` package, the eval needs it too; where the repo does not have it as a dependency, the eval uses the grep walk and says so in its output. Record its first result under `## Parity`. If the repo already has such a test (some apps pin crons to routes and cadences in a topology test), extend it rather than adding a second, and say so under `## Parity`. Run it; it must pass before you move on, because a `job_missed` check built on a wrong schedule raises findings every slot.

## 4. Write the door adapters

The adapters are written in this phase, one per door in the contract, because every door check and every later check reads a door through its adapter and nothing else. Dispatch the `door-adapter-writer` subagent once per door, in parallel where the doors share no files. Each brief carries: the door's row from `.watchdog/CONTRACT.md`, the door's semantic contract from `MAPPING.md`, the absolute path of the shared contract (resolve `../watchdog-build/references/shared-contract.md` from this skill's directory; a relative path resolves against wherever the subagent starts), the absolute path of `$KIT`, the vendored core path `lib/watchdog/core/`, and the client's schema or migration files for the tables the door reads. Where your agent cannot dispatch subagents, read `$KIT/agents/door-adapter-writer.md` and follow it yourself, one door at a time.

Each returns `lib/watchdog/doors/<door id>.js` (or `.ts`), its offline contract test `scripts/eval-door-<door id>.mjs`, the test's output, and any contract field it could not implement as written. Run every test yourself before accepting it; a returned "passes" is a claim, the exit code is the evidence. An adapter that could not implement its contract row leaves the door at the status the adapter can honestly support, and the contract row is not widened to match.

## 5. One door check per door, reconciling identities

For each door, write a check in `lib/watchdog/checks/door_<id>.js` using `$KIT/core/contracts/finding.d.ts` and the adapter from `lib/watchdog/doors/<id>`. The check lists the door's events in a bounded window, takes `proofOf` for each, and where the adapter has `proofOfProof`, reconciles identities: the provider's event id against the receipt's, the provider message id against the attempt's, never a count against a count, because one duplicate and one gap cancel in a count and hide both faults. Enumerate the expected scheduled occurrences from the schedule, not from the runs that exist, so a job that never started is still examined; a retry or a manual run never satisfies a different occurrence. Re-reading an old observation does not make it fresh: every source the check needs must be fresh and complete for the subject and interval before coverage is complete, and a stale, sampled, truncated or unavailable required source makes the check partial, whatever another source says. Each unknown or unsupported proof is reported as such in coverage, not swallowed. The check fills its Coverage honestly (examined subjects, truncation, fresh as of) so the core can tell silence from blindness. Write the offline eval for each with the fake harness in `$KIT/evals/lib/harness.mjs`: fires on a planted gap, stays quiet on healthy data, reports partial on a truncated page.

List each check under `## Doors` with its door, the proof it reads, what it reconciles against, and the status the door now has.

## 6. Create the reader, the writer and the approved views

From `## Fields` in `EGRESS.md`, write one migration that creates two roles with no default privileges:

- `watchdog_reader`, with `GRANT SELECT` on one view per approved source (each exposing only the allowlisted columns, with pseudonyms applied in SQL) and nothing else: no grant on any app table, on any watchdog table or on any notification table. The union of every adapter's and check's `reads` is the view list, so a read not on it fails at runtime, which is the correct outcome.
- `watchdog_writer`, with `SELECT`, `INSERT` and `UPDATE` on the watchdog's own tables (`watchdog_findings`, `watchdog_reviews`, `job_runs`, `watchdog_sweeps`, `watchdog_silences`, `alert_sends`) and no grant on any app table. Where the client's runtime can only hold one database credential and already uses a service connection, the writer may be that service connection instead; then say so under `## Role`, because the service connection can also write app tables, and the read-only client in the core is what keeps the checks off them.

Neither role gets a password in the migration, because a migration is committed. Both are created `NOLOGIN`. On the direct-connection path below, a human gives each a login and a password in their own database console; on the data-API path the roles stay `NOLOGIN` and the human mints a token per role instead. Either way the human stores each credential in an environment variable you name and record under `## Role` (for example `WATCHDOG_READER_DATABASE_URL` and `WATCHDOG_WRITER_DATABASE_URL`), in the place the client keeps secrets. You never see or print the value; the tests read the variable at runtime and fail with its name, not its contents, when it is missing. If the variable is not set when you reach the test, record a blocked step with the exact statement or token claim the human needs, minus any secret.

Then write `lib/watchdog/db.js`. The core talks to the database through a PostgREST-style query builder (`from(name).select(...).eq(...)`, the shape `$KIT/evals/lib/fake-postgrest.mjs` models), and `runWatchdog` and `runCronJob` each take one such client. Export one routing client whose `from(name)` hands an approved view to a reader instance and a watchdog table to a writer instance, and refuses any other name, so the one client the core holds still reads app data only as `watchdog_reader`. How the two instances reach Postgres depends on the access line under `## Stack`, and you record which under `## Role`:

- **Through the platform's data API** (the app already uses a hosted Postgres platform's JS client of that shape). Each role must be exposed there: granted to the API's authenticator role, with the views in a schema the API serves, and reached with a token whose role claim names it, minted by the human with the platform's signing secret and stored under its own variable name. This needs no new dependency, which is why it is the default for such an app.
- **Through a direct connection** (the app uses a Postgres driver). Write a thin adapter of the builder shape over the driver, covering only the methods the checks and the core call, each connecting with its role's connection string. If that adapter would grow past a small module, record the gap under `## Role` and as `unsupported` in the contract rather than half-building it.

Write the forbidden-write test (`scripts/eval-forbidden-write.mjs`): connect as the reader through the recorded variable, bypassing the routing client so the role itself is tested, attempt an insert into an app table, an insert into `watchdog_findings` and a select on an unapproved column, and assert all three fail; then, as the writer, attempt an insert into an app table and assert it fails. Every probe is one that must fail, so the test leaves no row behind wherever it runs, including production later. Record under `## Role` both role names, the writer's identity (role or service connection), the variable names, the views, the migration file and the test's result. Apply the migration the client's way; if that needs a human (a production credential you do not hold), record it as blocked with what is needed rather than working around it.

## 7. Write the artefact and stop

Fill in the five sections of `.watchdog/HEARTBEATS.md` (the sweep route, its schedule and the self check go under `## Jobs`; the adapters and their tests under `## Doors`), run the parity eval, the contract drift eval, the adapter tests, the door evals and the forbidden-write test once more, and stop. Say what you wrote: jobs wrapped, jobs mapped from existing sources, jobs with no heartbeat, adapters written, doors checked with their status, the reader, the writer and the views created, and every eval's result. There is no decision for a human here unless something blocked you, most often the reader's login; if it did, say exactly what you need.
