# watchdog-page

You are building the place where every finding is judged. The page is how the watchdog earns the right to act: precision is measured from the verdicts given here, and a page that is slow to judge on produces fewer verdicts and a weaker measure. Read `../watchdog-build/references/shared-contract.md` first, then `.watchdog/CANVAS.md` (the approved design brief), `.watchdog/EGRESS.md` and `.watchdog/CHECKS.md`. Build in the client's own stack and tokens, in its own routing (a file route, a router entry), behind whatever the app already uses to keep a page to its operators (an owner or admin role, an allowlist of operator accounts), and link subjects by the routes the canvas names. Where the app has no such gate, do not invent one or ship the page open: record it as blocked under `## Page` with what is needed, because the page shows findings about customers.

Report-only holds for the page as for the sweep: the page never reads app tables at all, and its reads and the verdict write go through the writer from `lib/watchdog/db.js`, which can see the watchdog's tables and nothing of the app's.

## 1. Build the page from the canvas

Follow the canvas part by part: the title with the folded receipt line, the uptime strip, the findings column with its tabs, the finding cards with evidence rows and the folded would-do and would-say (a card whose `reopened_count` is above zero carries a "back again, nth time" label, because a fault that returns after resolution is a regression and is read differently from a new one), the verdict row, the checks rail with its scoreboard and recent sweeps, and the empty, erroring and unknown-door states. Build the cards to the contract's "a card reads in ten seconds" invariant: plain by default, with a context line naming the subject, fact rows under plain labels (a model finding uses the `evidence.labels` the review stored; a rule finding hides ids, hashes and sweep bookkeeping through one list of hidden keys and labels the rest from one map of key to words), and a page-level dev mode switch for the exact refs, quotes, keys, model details and trace link. Read `../watchdog-explain/references/page-anatomy.md` for what each mode shows. Keep the page's data shaping in a pure module (`lib/watchdog/page-model.js`) so the evidence rows in both modes, the context line, uptime buckets and verdict totals can be tested offline with a fixed `now`; the eval must hold one case per rule check that no plain row's value is an id. Timestamps render in the client's zone; ages are computed at render time, never stored. Keep WCAG AA contrast, visible focus rings and `prefers-reduced-motion`.

A read of findings goes through a route behind that gate that selects from `watchdog_findings` and `job_runs` with no joins into app tables, because the page must show only what the egress policy already let into the finding.

## 2. Build the trace

`/watchdog/<id>` tells one finding's story in order: inputs (the rows a rule check read, filtered to the subject, matching rows highlighted; or the packet as sent, loaded on demand, with model, key name, tokens and cost), decision (the rule in words and the values that met it; or the raw model answer with each ref's match result and what was dropped and why), and what went out (the finding row, the alert state from `meta.alerts`: "no route can send at report-only", "would alert on owner_email", "sent, proof <id>" or "capped", the would-say text held back). The trace is what lets a human say "false alarm" and point at the value that misled the check, so every number on it must be the stored one, not recomputed.

## 3. Verdicts

Three keys per card, Correct, False alarm, Unsure, with an optional reason, and the keyboard path from the canvas. The verdict route writes the verdict columns and `meta.verdict_context` from `$KIT/core/verdicts.js`, so a finding that later changes or reopens reads as to review again with the old verdict kept beside it. System findings stay out of the totals. Verdicts are the only human write the watchdog tables take, and the route must refuse any other field.

## 4. Alert routes

Alerts are how a finding reaches a person who is not looking at the page. Read `references/alert-routes.md` first: it fixes the two contract levels. At report-only, which is where this build ships, the runtime has nothing to send with, so what you build here is the routing and the previews: `lib/watchdog/alerts.js` with the fixed enum of alert kinds mapped from finding kinds, the grouping that makes one incident on one scope one alert rather than one per sweep, the caps, and the rendered payload (finding id, kind, severity, scope key, page and trace links, nothing else), recorded on each finding under `meta.alerts` so the page shows "would alert on owner_email". The sender (`lib/watchdog/alerts/send.js`, the `alert_sends` door with its claim-then-prove rows on the table from `$KIT/core/sql/0006_alert_sends.sql` and a recipient-side dedupe key) is written and covered by the offline evals for the `alert_payload_bounded` and `alert_send_idempotent` gates, and is given no credential, no notification-table grant and no live setting in this phase. Record under `## Alerts` the routes, their caps, the evals' results and the sentence "no route can send at report-only; activation is a separate authorised change".

Where `MAPPING.md` lists an existing monitoring system, deduplicate attention, not findings: the existing system keeps its notifications, the watchdog suppresses only the route for that finding's condition and occurrence (recorded under `meta.alerts`; unrelated kinds keep theirs), and the page shows a confirmed match as "already reported by {system}" beside the finding with the external state and its observation time. Match only through a declared deterministic rule on the same scope, an exact shared subject or event identity, a compatible condition and the same occurrence; similar wording or nearby timestamps never match, and a provider-wide incident is context unless its evidence names the finding's subject. Store the system, incident id, approved link, rule, supporting refs, observed state, observation time and freshness limit under `meta.existing_monitoring`, written by the sweep and fenced by generation, outside the finding id and the verdict fingerprint. A match never hides a finding, changes its severity, assigns a verdict, resolves it or excludes it from adjudication; an unreadable or stale source leaves the historical link and marks the current state unknown.

## 5. Hub projection

Where the human asked for a central view across installations, build the projection the hub pulls: `GET /api/watchdog/summary` returning the bounded aggregate in `references/alert-routes.md` under Hub projection (installation, scope key, contract level, sweep id, counts by check and severity, open and judged totals, uptime summary, receipt summary; never a finding's text or evidence), read from the watchdog's own tables only, through the core's read-only wrapper over the writer, behind a bearer token named in an environment variable and listed in `EGRESS.md`. The watchdog never posts to the hub, so a hub outage cannot touch a sweep and the hub detects a silent installation itself when the sweep id stops moving. Validate the projection against the schema in an offline eval. If no hub was asked for, say so under `## Hub` and build nothing.

## 6. Write the artefact and stop

Run the page-model evals (`node scripts/eval-watchdog-page-model.mjs`, offline with a fixed `now`, plus the alert evals and the hub projection eval) and the client's own build, using the build script in `package.json` and any wrapper or lock its scripts already put around it, never a bare framework command that skips them; then write `.watchdog/PAGE.md` from `$KIT/templates/PAGE.md` with the five sections: the routes and components built, the trace, the verdict route and its context rule, the alert kinds and their caps, and the hub decision. Stop. Say what you wrote and that no route can send at report-only; there is no decision here unless the canvas could not be followed, in which case say what you changed and why.
